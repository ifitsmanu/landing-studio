# Governance

Landing Studio uses a maintainer-led open-source model.

## Roles

- **Contributors** propose changes and participate in review.
- **Reviewers** have demonstrated project knowledge and can approve scoped changes.
- **Maintainers** merge changes, manage releases and security reports, and enforce project policies.

## Decisions

Routine changes use pull-request consensus. Material changes to schemas, release gates, licensing, supported runtimes, or ethical constraints require a public proposal and maintainer approval. When consensus is not possible, the lead maintainer makes the decision and records the rationale.

## Maintainer expectations

Maintainers disclose conflicts, protect embargoed reports, avoid self-approving high-risk changes when another reviewer is available, and base release claims on retained evidence. Inactive maintainers may move to emeritus status. New maintainers are nominated based on sustained high-quality contributions and responsible review.

## Releases

Releases follow semantic versioning. A release requires passing automated gates, a clean independent red-team result for P0/P1 findings, a changelog, and reproducible artifacts. Security releases may use an abbreviated private process until coordinated disclosure.
